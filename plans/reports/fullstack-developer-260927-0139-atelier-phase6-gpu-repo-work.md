## Design notes worth flagging

- **`gpu.py` has no `Worker` import** (avoids the obvious circular import, since `worker.py` imports `gpu`). The header badge instead calls `gpu.summarize(worker.status, backend, conn)`, passing the `GpuStatus` instance directly rather than the whole `Worker`.
- **`GpuStatus.get(backend, conn, force=False)`** always acquires its per-backend `asyncio.Lock` (cheap when uncontended) and re-checks staleness after acquiring it, so concurrent readers share one real refresh without a separate fast-path pre-check.
- **`gpu.start_warm`** takes a plain `deployed: bool` (not the gateway/`AppState`) so `gpu.py` stays free of any gateway round-trip; the route fetches a `force=True` status first and passes the flag in, refusing with `BackendStopped` when the app isn't deployed.
- **`Worker.stop_backend`/pinger deadlocking avoided**: the breaker's `stop_backend(confirm=True)` is always scheduled via `asyncio.create_task`, never awaited inline, because the pinger calls it while already holding `locks[backend_id]` — the same lock `stop_backend` needs.
- **A real bug caught by the tests**: `cancel_all_for_backend`'s original `BEGIN IMMEDIATE` (mirroring `cancel_job`'s pattern) collided with the implicit transaction SQLite's legacy `sqlite3` module opens as soon as `gpu.clear_warm`'s `UPDATE` runs earlier in the same `stop_backend` session block (`cannot start a transaction within a transaction`). Fixed by dropping the explicit transaction from `cancel_all_for_backend`: unlike the HTTP-request-triggered `cancel_job`, it is only ever called from inside `stop_backend`, which already holds `locks[backend_id]` for its whole sequence (mutual exclusion against the dispatcher/pinger is already guaranteed there), so the outer `session()` block's own commit/rollback is sufficient.
- **Test-only constructor parameters added to `Worker`**: `converge_poll_interval_s` and `pinger_step_s`, both defaulting to the production values (5s/5s), added purely so tests don't need multi-second real sleeps — same rationale as the pre-existing `dispatch_interval_s`/`poll_interval_s`.
- No existing test file required a behavior-expectation change; the whole prior suite (312 tests) still passes unmodified. The route-crawl (`test_auth.py`) and secret-leak crawl (`test_pages_hide_secrets.py`) tests picked up `/gpu` and `/gpu/panel` automatically (they walk live `app.routes`) with no edits needed.

## Re-review fixes

A re-review (appended to the same review file, "Re-review" section) confirmed every High and Medium finding fixed, then found six new Low regressions introduced by the first fix round (R1–R6) plus 13 of 33 new mutants aimed at that round's own code surviving. ### R1 (must-fix): orphaned CLI child on an outer cancellation
`_bounded_step`'s `asyncio.timeout(remaining)` cancels whatever `_modal_cli` is awaiting with the builtin `CancelledError`, not `TimeoutError`, whenever the outer per-step budget runs out before the CLI's own internal 30s timeout. The old `except TimeoutError: proc.kill(); await proc.wait()` never saw that exception type, so the child was neither killed nor reaped. Split the process-handling logic out of `_modal_cli` into a new, directly testable `_run_cli_subprocess(argv, *, timeout, on_spawn=None)`, and added `except BaseException: proc.kill(); await proc.wait(); raise` after the existing `TimeoutError` branch. `on_spawn` is a test-only hook (never passed by production callers) that reports the child's pid.

Test: `test_run_cli_subprocess_kills_and_reaps_the_child_on_outer_cancellation`, parametrized over the default event loop and `uvloop` (production's loop) — spawns a real `sleep 5`, cancels it after 0.2s via an outer `asyncio.timeout`, and asserts `os.kill(pid, 0)` raises `ProcessLookupError` afterward. Verified this fails before the fix (manually reverted the `except BaseException` branch, confirmed `DID NOT RAISE ProcessLookupError` on both loop variants, then restored it) and passes after.

### R2: duplicate `app list` per convergence iteration
`stop_containers` gained an optional `app_state: AppState | None = None` parameter (also added to the `ModalGateway` protocol and the fake); `_stop_backend_locked`'s loop now passes its own already-fetched `AppState` through instead of `stop_containers` re-fetching one internally. Test: `test_stop_reuses_the_app_state_read_across_stop_containers` asserts exactly one `app_state()` call for a converging pass, and that `stop_containers` received a non-`None`, `"deployed"` state (`FakeModalGateway.stop_containers_app_state_args`, a new recording list).

### R3: the cancel phase ran before the deadline existed
`deadline = self.clock() + CONVERGE_S` now runs *before* `_cancel_all`, not after, and `_cancel_all`/`_cancel_once` take that `deadline` and cap each attempt at `min(_CANCEL_TIMEOUT_S, remaining)` (`_CANCEL_TIMEOUT_S` reduced from 30s to 10s). Worst case is now cancel (≤2 attempts × ≤10s) plus convergence, sharing one ~60s budget, instead of a fixed cancel phase stacked on top of a separate 60s convergence budget. Tests: `test_cancel_once_is_bounded_by_the_deadline_it_is_given` (a hanging cancel cut off at ~0.3s, not 10s, when given a near-expired deadline) and `test_stop_computes_the_deadline_before_the_cancel_phase` (a full `stop_backend` call with a hanging cancel and a pre-exhausted fast-forward clock returns in well under 5s, not 30s).

### R4: an empty timeout message
`str(TimeoutError())` is `''`. `_bounded_step` now special-cases `except TimeoutError` to build `f"{label}: timed out after {remaining:.0f}s"`, and falls back to `str(exc) or type(exc).__name__` for any other exception whose text happens to be empty (e.g. a bare `RuntimeError()`). Tests: `test_bounded_step_reports_a_readable_timeout_message`, `test_bounded_step_reports_a_readable_message_for_a_non_timeout_failure`.

### R5: `_STOP_STEP_TIMEOUT_S` was dead code
`_bounded_step`'s `remaining` computation now uses `max(0.5, min(_STOP_STEP_TIMEOUT_S, deadline - self.clock()))`, so one step is capped at 30s even when the overall deadline is still far away, and its comment states this. Test: `test_stop_step_timeout_caps_each_step_even_with_plenty_of_budget_left` spies on `asyncio.timeout`'s own argument (no real waiting) and asserts it receives `_STOP_STEP_TIMEOUT_S`, not the far-off deadline's full remaining budget.

### R6: one transient app-state failure showed "unknown" for up to 60s
`GpuStatus` gained `_app_state_error_since` and two new constants: `_APP_STATE_ERROR_RETRY_S = 10.0` (a failed app-state read is retried this soon, not after the normal 60s success TTL) and `_APP_STATE_ERROR_GRACE_S = 30.0` (an error is suppressed from the returned view — the page keeps showing the last known-good state — until it has stood for this long). The grace only applies when there **is** a last known-good state to fall back on (`backend.id in self._app_state`); the very first-ever failed read, with nothing cached yet, still shows "unknown" immediately, not "stopped" (an early version of this fix defaulted to the wrong state here — caught by `test_status_shows_unknown_and_negative_caches_a_failing_gateway`, already in the suite, going from `'stopped' == 'unknown'` failing to passing once corrected). Tests: `test_a_transient_app_state_failure_keeps_the_last_good_state_during_a_grace_period`, `test_a_failed_app_state_read_is_retried_sooner_than_a_successful_one`.
